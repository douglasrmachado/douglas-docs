# About Me

I'm a Technical Writer with a background in software development. That combination shapes how I approach documentation: I read the code and the API before I write about it, and I treat docs as a product with real users, not as an afterthought to engineering.

I currently work with technical documentation for SaaS and API-based products, writing for developers and other technical readers who need to get from "what is this?" to "it works" as quickly and clearly as possible.

## What I focus on

- **API documentation**: reference docs, endpoints, authentication, and error handling that developers can act on without guessing.
- **SDK documentation**: installation, usage, and examples for the libraries that wrap those APIs.
- **Git and GitHub workflows**: writing and reviewing docs the same way engineers ship code.
- **Docs as Code**: treating documentation as a versioned, reviewable part of the product. More on that in [Docs as Code](/docs/docs-as-code).
- **Documentation reviews**: reading docs, mine or a teammate's, for accuracy, structure, and whether they actually answer the reader's question.
- **Documentation automation**: reducing manual, repetitive work in how docs are built, checked, and published.

## How I like to work

Because of my development background, I'm comfortable working directly in a codebase: reading source, following pull requests, and using the same tools engineers use, rather than requesting a summary secondhand. I'd rather ask a specific question in a PR thread than publish a guess.

This site is an example of that in practice: it's built with [Docusaurus](https://docusaurus.io/), managed as a Docs as Code project, and the content is deliberately kept close to how I actually write: plain, structured, and easy to scan.
